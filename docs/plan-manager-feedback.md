# План: замечания IT-менеджера (2026-11-25)

Рабочая заметка: что просили, как это ложится на текущий код и ТЗ (`tz.pdf`), в каком порядке делаем.
Каждый этап — отдельная ветка и PR, с тестами (Pest, в контейнере на sqlite — см. память проекта).

## Что уже есть в коде (на чём строим)

- Меню: `categories`, `dishes` (цена int в тенге, `station` kitchen/bar), стоп-лист `stop_list_entries` (morph: блюдо/категория).
- Заказы: `orders` (source waiter/qr/booking/online/phone, channel hall/delivery/pickup, status open/bill_requested/paid/cancelled/refunded,
  `discount_percent`/`discount_amount`), `order_items` (снимок названия и цены), `payments` (cash/card/mixed), `tips`.
- Доставка: `deliveries` (new → accepted → cooking → ready → on_way → delivered/issued | cancelled). Онлайн-заказ приходит в `new`,
  позиции в статусе `draft`, на кухню уходят только по кнопке администратора (`DeliveryService::sendToKitchen`).
- Гости: `guests` (телефон уникален), `orders.guest_id`. Бонусов, постоянной скидки гостя пока нет.
- Роли/права: `roles` + `role_permissions` (enum `Permission`), у пользователя одна роль. Филиалов нет — всё глобально.
- Залы/столы: `halls`, `dining_tables` (qr_token), удаление стола с историей = `is_active=false` (TableService, HallService).
- Настройки: `settings` key/json. SMS-шлюза нет.

## Порядок (и почему)

1. ✅ **Быстрые правки** (#8, #6, #7a, #7c) — ветка `feat/quick-fixes-stage1`. #8: удаление стола = soft delete (`deleted_at`, уникальность номера только среди живых).
2. ✅ **Экран «Заказы»** (#9 + #7b) — ветка `feat/orders-monitoring`: `/orders`, право `orders` (админ зала, бухгалтер), карточка заказа в боковой панели.
3. ✅ **Тип продукции + акционные цены** (#1, #10) — ветка `feat/product-kind-sale-prices`: `dishes.kind` (made/resale), `sale_price` + `sale_from/sale_until`; цена продажи везде через `Dish::currentPrice()`.
4. **Продукты + калькуляция** (#2).
5. **Склад: приход, списания, инвентаризация, «Нужно закупить»** (#3) — с `branch_id` (см. ниже).
6. **Бонусы** (#5) — общие на сеть, филиалы не нужны.
7. **Смены** (#7d) — с `branch_id`.
8. **Филиалы** (#4) — отложены (решение 2026-11-25): Про-версия по ТЗ, реального клиента с несколькими точками пока нет.
   Полный этап: `branch_id` в залах/столах/заказах/кассе/стоп-листе/ценах, скоупинг запросов, сотрудник ↔ филиалы, переключатель, отчёты по филиалам.

**Зацепка под филиалы (делаем сразу, вместе со складом):** таблица `branches` с одной записью «Основной филиал» (без интерфейса);
во всех **новых** таблицах, которые по ТЗ «свои в каждом филиале» (остатки, движения склада, инвентаризация, смены), — `branch_id` NOT NULL
с филиалом по умолчанию. Тогда при включении филиалов переделываются только старые таблицы (залы, заказы, касса), склад и смены — нет.

## Решения (2026-11-25)

- **Филиалы — меню:** общее меню сети; в каждом филиале блюдо включается/выключается, можно своя цена и свой стоп-лист (`branch_dish`: branch_id, dish_id, is_available, price nullable). Как в ТЗ разд. 4.
- **Бонусы — подтверждение:** пока без SMS-кода — кассир находит гостя по телефону, списание пишется в журнал. Под SMS-код оставить точку расширения (интерфейс подтверждения), включить, когда появится шлюз.
- **Акционные цены:** фиксированная акционная цена в TMT + необязательный период `с–по`; в меню старая цена зачёркнута.
- **#7c:** «моб. приложение» = страница для гостей. Делаем обязательный шаг «Подтвердил звонком» перед кухней + плашка «ждёт звонка».
